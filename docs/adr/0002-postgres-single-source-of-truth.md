# ADR-0002: Postgres as the single source of truth

**Status:** Accepted
**Date:** 2026-10-06

## Context

The system needs relational business data, vector search for memory retrieval, durable agent
checkpoints, a job ledger, and an append-only usage and audit log. Each of those has a
purpose-built product available.

## Decision

Cloud SQL Postgres 16 holds all of it: business tables in `app`, LangGraph checkpoints in
`langgraph`, audit log in `audit`, rollups in `analytics`, and vectors via `pgvector` with an
HNSW index. Queues carry pointers; they never carry state.

## Consequences

**Easier:** one backup and point-in-time-recovery story; one migration tool; transactional
consistency between a memory write and the run that produced it; local development is one
container; a self-hoster operates one database.

**Harder:** the database is the scaling chokepoint, so connection management matters a great
deal (see ADR-0004 and the infra rules). Vector search will eventually be slower than a
dedicated engine at very large corpora.

**Live with:**

- `pgvector` columns are fixed-dimension, so one embedding model is pinned per deployment and a
  model change is a documented four-step backfill.
- Cloud SQL has a fixed extension allowlist. `pg_uuidv7` is unavailable, so UUIDv7 keys are
  generated in Python.
- LangGraph's tables are owned by its own library and must be isolated from Alembic — enforced
  by a CI check, because an autogenerated migration there would corrupt live suspended runs.

## Alternatives considered

**A dedicated vector database** (Pinecone, Qdrant, Vertex Vector Search). Rejected: a second
datastore means a second consistency problem, a second backup story, and a second bill, for a
corpus that is small per tenant. Revisit if a p50 memory set exceeds roughly 1000 entries and
retrieval latency becomes measurable.

**Firestore or another document store for chats.** Rejected: the data model here is genuinely
relational — grants, memberships, versions, and ledgers all want foreign keys and joins.

**AlloyDB.** Rejected: three to five times the cost, and its advantages are analytical rather
than transactional.

**Spanner.** Rejected: no `pgvector`, no credible Alembic story, and horizontal scale we do not
need.
